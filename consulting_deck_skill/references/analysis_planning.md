# 分析规划与结论综合 · v6

> v9适用原则：下列字段、编号、评分和布局预算用于复杂任务的按需参考，可合并或省略不影响结果的过程记录。分析/编码正确、核心内容可读完整与同版交付是底线；默认阈值和作者选择的区别见 [开放创作](open_authoring.md)。

S1–S3使用。先读本文件，再按 [方法路由](framework_router.md) 只读所需方法卡。
本流程是本项目对公开方法的执行适配，不代表任何咨询公司的内部标准。

## 1. 按任务选择深度

在brief记录`work_mode`及理由，优先服从用户的任务范围。

| work_mode | 适用 | 必要工作 | 可以省略 |
|---|---|---|---|
| analytical | 原始数据、访谈、多份资料，需要诊断或建议 | 议题与竞争假设、分析计划、实际分析、结论综合、内容覆盖、分析验收 | 与决定无关的模型、无影响的补研究 |
| exploratory | 问题尚不清楚的行业研究或材料探索 | 界定对象与范围、建立研究地图、EDA/文本编码、形成问题与发现、记录未知 | 预设推荐、为每段资料编造假设 |
| editorial | 用户已确认内容，要求改写、排版或转成deck | 必要算术/时点/状态核对，修正与未知，原文段落到页面的去向 | 新研究、财务建模、议题树、完整任务/发现台账、逐值证据JSON、逐项AQ表 |

editorial不把客户文字自动标为verified。发现错误时定位原文、提出收窄措辞或证据缺口；必要的局部核对继续做，涉及改变任务目标才询问。不得为了填表重新发明用户已确认的方向。
**editorial的最小交付**：在标题骨架前附一段范围/主题说明和简短核对记录（实际公式、状态修正、未决项），重要调整保留原文定位和理由。可全部放在ghost_deck.md；无需单独brief、analysis_plan、findings、content_map或analysis_review文件，也不要求Q/T/F/E编号和下文全字段。只为重要数字或有争议的判断保留详细依据。一般正确句子不逐项编码，不把同一内容在多张表反复登记。

下文完整结构供复杂analytical/exploratory任务按需采用；小型分析可合并为analysis_brief.md，合并不省略实际分析或关键结论依据。editorial仅在发现局部复杂问题时对受影响部分调用相应任务/方法，不因一个笔误把全篇升级为分析项目。

## 2. 从资料到问题

1. 从brief提炼：谁在何种时点，需要理解什么或选择什么；候选行动、现状基准、资源/期限约束、成功标准是什么。没有决策请求的研究报告以理解目标替代行动选项。
2. S1先做足以理解材料的清单与口径检查，不先穷尽抽取，也不等最终标题才搜证据。围绕问题和竞争假设定向补证据；新发现回写清单。
3. 复杂问题可用议题树（`Q-*`为可选编号）：同层采用相同拆分依据，标出交叉依赖，区分恒等式拆分与待验证的原因。详见 [逻辑框架](logic_frameworks.md)。
4. 每个重要诊断议题列竞争解释、支持信号、可能推翻它的证据。初步答案标“工作假设”；探索研究允许从异常与开放问题开始。
5. 按对结论的影响、可改变程度、未知程度和取证成本排序。先做可能改变建议的分析；不强制80/20比例，也不为了证明覆盖全面而运行全部模型。

## 3. analysis_plan.md：分析蓝图

先让读者看到核心问题、议题树和工作计划；已有授权时记录并继续，不新增逐阶段签字。

| task_id | question_id及问题 | 假设/竞争解释 | 方法ID与采用/淘汰理由 | 输入与口径/证据ID | 分析步骤与预期输出 | 反证/判定条件 | 缺口、优先级与状态 |
|---|---|---|---|---|---|---|---|
| T-01 | Q-01 收入降幅集中在哪 | 渠道结构贡献；不预设根因 | FM-01；暂不做DA-02，缺SKU量价 | E-01…；同年净收入 | 重算分项差值、总差值及贡献表 | 分项和不闭合则先核对范围 | 可执行；优先处理 |

每项任务必须说明输出会帮助回答什么，不能只写“做五力”“画瀑布图”。
状态用`planned / running / completed / blocked / not_applicable`；completed表示工作完成，不保证假设成立。blocked要有缺失字段、影响和下一步；not_applicable要有理由。
期望输出是比较表、估计区间、假设判定或缺口清单，不能预填期望结论。

方法选择依次判断：

`问题类型 → 业务机制 → 数据可用性与口径 → 方法假设 → 最简单够用的方法 → 核验与回退`

一个问题可以组合方法；一种方法可以服务多个议题。无命名框架适用时，用透明的自定义分析，记录输入、步骤和边界，无需先注册`CUSTOM-*`编号；不得为了匹配现有卡片改变问题。

## 4. 实际分析与 findings.md

分析不能以一份计划代替。执行筛选、聚合、公式计算、案例对照或文本编码，保存可复算的工作表/脚本/公式、输入定位及结果。没有运算的定性分析保存比较维度、引文与推理过程。
表格/计算脚本中的假设、输入与输出分开；未知保留null，不能把0当缺失。派生值保留输入定位与公式；已建立evidence时同步重要结果。

复杂分析的重要发现可按下表组织；小任务用连贯文字保留实质依据即可：

| 字段 | 要求 |
|---|---|
| finding_id / question_id / task_id | 用`F-* / Q-* / T-*`串联；一项发现可有多个任务 |
| statement / claim_type | `descriptive / diagnostic / forecast / recommendation`；一句话保留适用范围 |
| evidence_ids / result_locator | 原子证据与计算/编码结果的位置，不能只有方法名称 |
| reasoning | 数据到判断之间的推理；会计分解不写成因果识别 |
| hypothesis_status | 诊断任务使用`supported / refuted / unresolved / mixed`；非假设任务可不适用并解释 |
| counterevidence / alternatives | 支持相反结论的证据、尚未排除的解释；没有找到不等于不存在 |
| confidence / limitations | 依据和局限，区分来源可靠性与推断强度，不机械打精确概率 |
| decision_effect / change_condition | 对理解或选择的影响，什么新证据/阈值会改变判断；阈值注明来源或为建议 |

综合时检查任务之间的依赖、矛盾和重复计算。定性访谈能揭示机制和提出假设；没有抽样依据不能推断全市场比例。
建议比较可行选项与现状基准，说明收益、成本、风险、现金和执行条件。缺少这些信息时可形成“建议验证X”，不能升格为“已证明应全面投入X”。
用户期望目标单列`target`，模型产生的预测单列`forecast`；不得倒推假设使二者相等。

## 5. content_map.md：重要内容的去向

材料登记与问题覆盖是两项检查。先映射到议题/发现，S3再填章节与页码；不必在分析开始前冻结每页。

| material_id与原文位置 | evidence_ids | question_ids / finding_ids | 作用 | 去向 | 采用/不采用理由 |
|---|---|---|---|---|---|
| SRC-01 销售表2024–25渠道列 | E-01… | Q-01 / F-01 | support | 正文P02；附录计算表 | 支持降幅构成，不支持原因 |
| SRC-02 客户访谈第8段 | E-20 | Q-02 / F-02 | counterevidence | 正文P03限制；附录原文 | 产品问题尚未排除 |

作用：`support / counterevidence / context / duplicate / out_of_scope / unresolved`。
去向：正文、附录、暂不采用、待补；重要材料不能无理由消失。多个来源重复转述同一报告不能算多份独立支持。
逐个关键议题检查：有回答、明确未知，或经说明移出范围。重要反证即使原文进附录，也必须在正文相关结论中体现。

## 6. 进入综合的检查与反馈

analytical/exploratory按 [分析验收](analysis_review.md) 生成`analysis_review.md`，逐项写依据、未决项、允许结论的边界。editorial以简短核对结论记录实际检查范围及必要限制，不生成全套AQ表。
`ready`表示可按当前范围形成报告；`ready_with_limits`表示可以形成有明确未知的报告；`rework`表示现有断言仍有误导，先修正分析或收窄断言。
关键问题未解可交付缺口或验证计划；不能一边标未知，一边保留依赖它的确定推荐。
S3将findings组织成storyline；S4–S7发现来源或推理问题，回到受影响任务，更新发现、标题、内容去向及相关数值，再复核受影响部分。无需重跑无关模型或让用户重复确认。

公开依据：McKinsey的[七步问题解决法](https://www.mckinsey.com/capabilities/strategy-and-corporate-finance/our-insights/how-to-master-the-seven-step-problem-solving-process)支持问题定义、拆解、优先级、工作计划、分析与综合的迭代。表格、ID、状态和门禁为本项目设计。
